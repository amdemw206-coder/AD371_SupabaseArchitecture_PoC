PostgreSQL as the Single Source of Truth

Supabase rejects proprietary vendor lock-in by wrapping time-tested, enterprise-grade open-source tools around a powerful PostgreSQL relational database. Instead of proprietary abstraction layers, Supabase treats PostgreSQL as both the data store and the extensible application engine, routed via high-performance Envoy edge gateways.

Composable Open-Source Stack

Each subsystem is a standalone open-source project (PostgREST, GoTrue, Realtime, Storage API) connected seamlessly through Envoy API gateway and native Postgres database triggers & roles.

Zero proprietary vendor black boxes

Database-First Security (RLS)

Authorization logic is delegated straight to Postgres Row Level Security (RLS) policies. JWT claims are injected directly into Postgres session variables (`request.jwt.claim.sub`).

Granular row & column protection

Extensibility via Extensions

Leveraging powerful Postgres extensions like `pgvector` for AI embeddings, `pg_cron` for scheduling, `pg_net` for webhooks, and `PostGIS` for geospatial mapping.

Unmatched database extensibility

Why PostgreSQL as the Core Engine?

In traditional serverless or NoSQL architectures (like Firebase), application logic is split between client SDKs, middle-tier custom serverless functions, and document databases with proprietary security rules DSLs.

Supabase flips this model. Because Postgres has a robust execution engine, connection pooling (Supavisor), and full-text search built in, clients can talk directly to the database via auto-generated REST and GraphQL APIs without an intervening custom Node.js/Python server.

// Traditional vs Supabase Data Flow
# Traditional
Client -> API Gateway -> Custom Express/Node Server -> ORM -> DB
# Supabase Architectural Pattern
Client -> Envoy Gateway -> PostgREST / GoTrue -> PostgreSQL (RLS Enforced)

Core Components Breakdown Matrix

Detailed breakdown of the open-source microservices powering the Supabase ecosystem.

API & Edge C++ / Envoy

Envoy API Gateway

High-performance cloud-native edge proxy handling SSL termination, global traffic routing, rate limiting, and secure request forwarding to downstream internal microservices.

Underlying Tech: Envoy Proxy
System Role: Edge Gateway & Proxy
Auth & Security Go

GoTrue (Auth)

A JSON Web Token (JWT) based API server that manages users, issues JWT tokens, handles OAuth providers (Google, GitHub, Apple), magic links, and multi-factor authentication (MFA).

Underlying Tech: GoTrue (Go)
Database Role: auth schema tables (`auth.users`)
API Layer Haskell

PostgREST

Turns any PostgreSQL database directly into a zero-boilerplate RESTful API. Automatically inspects database schemas, foreign keys, and RLS policies to serve fast JSON queries.

Underlying Tech: PostgREST (Haskell)
Database Role: Direct SQL-to-JSON mapping
Data & Storage Elixir

Supavisor

Cloud-native, scalable PostgreSQL connection pooler and process supervisor built in Elixir. Manages heavy concurrent client connections with session and transaction pooling modes.

Underlying Tech: Supavisor (Elixir)
System Role: Connection Pooling & Routing
Realtime Elixir

Realtime (Phoenix)

Allows developers to listen to PostgreSQL changes (INSERT, UPDATE, DELETE) via WebSockets using Postgres logical replication features. Also supports multi-user Presence and Broadcast channels.

Underlying Tech: Phoenix / Elixir
Database Role: Postgres Logical Replication (WAL)
Data & Storage Node.js

Storage API

Manages large files such as images, videos, and documents. Uses standard S3-compatible object storage backend while storing file metadata directly in Postgres with RLS security rules.

Underlying Tech: Fastify / Node.js + S3
Database Role: `storage.objects` table + RLS
Database Core Node.js

postgres-meta

A REST API for managing your PostgreSQL database. Allows querying tables, columns, schemas, extensions, roles, and executing SQL migrations programmatically.

Underlying Tech: Node.js / Express
System Role: Database Metadata Management
Compute TypeScript

Edge Functions

Serverless TypeScript functions distributed globally on Deno Deploy. Perfect for running custom business logic, interacting with third-party APIs (Stripe, OpenAI), and webhook handling.

Underlying Tech: Deno / V8 Engine
Database Role: Triggered via `pg_net` or HTTP
Management UI Next.js / React

Studio Dashboard

The official open-source graphical dashboard interface for managing databases, tables, Auth policies, Edge Functions, SQL editor, and bucket storage configurations.

Underlying Tech: Next.js / React / Tailwind
System Role: Unified Management UI

Functional PoC: RLS & JWT Auth Sandbox

Test how Supabase delegates security and authorization directly to the database via JWT claims and PostgreSQL Row Level Security (RLS).

1. Select User Role / Context

2. Injected JWT Claims

Passed to Postgres Session
{ "iss": "supabase", "sub": "a1b2c3d4-user-42", "aud": "authenticated", "role": "authenticated", "email": "student@university.edu", "exp": 1893456000 }

Postgres reads these claims via auth.uid() and auth.jwt() during query execution.

3. Active RLS SQL Policy

CREATE POLICY "Users can read own todos"
ON public.todos FOR SELECT
USING (
  auth.uid() = user_id
  OR
  current_setting('request.jwt.claim.role') = 'service_role'
);

4. Database Table (`public.todos`) Result

Simulating: SELECT * FROM todos; executed through PostgREST with RLS filter applied.

Academic Takeaway

Notice how anonymous users see 0 rows, regular users only see their own rows (user_id: 42), and admin users bypass standard user restrictions. Because this security is enforced at the PostgreSQL kernel level, even if a developer makes a mistake in the API query code, the database refuses unauthorized access.
